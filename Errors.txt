🏭 خطاهای Ansible در محیط‌های عملیاتی Production — راهنمای جامع DevOps/SRE

    این راهنما بر پایه تجربه واقعی محیط‌های عملیاتی است. هر خطا با سناریوی وقوع → پیام دقیق → ریشه فنی → رفع فوری → رفع دائمی → پیشگیری توضیح داده می‌شود.

📡 دسته ۱: خطاهای اتصال SSH و شبکه
1.1 UNREACHABLE! Failed to connect to the host via ssh: Connection timed out during banner exchange

سناریو: اجرای playbook روی ۵۰ سرور، ناگهان ۳۰٪ unreachable می‌شوند — معمولاً صبح‌ها پس از بکاپ شبانه.

ریشه فنی:

    MaxStartups در sshd (پیش‌فرض 10:30:100) — پس از ۱۰ اتصال همزمان، ۳۰٪ رد، از ۱۰۰ رد کامل

    fail2ban روی هدف به‌دلیل تلاش‌های ناموفق قبلی، IP کنترل‌نود را ban کرده

    ControlPersist سوکت قدیمی گیر کرده

    فایروال/NAT حداکثر تعداد اتصال concurrent session را می‌بندد

رفع فوری:
bash

# از کنترل نود
rm -rf ~/.ansible/cp/*
ssh -o ConnectTimeout=5 -o BatchMode=yes user@target 'echo ok'

# روی هدف
sudo fail2ban-client status sshd
sudo fail2ban-client set sshd unbanip <control-node-ip>
sudo sshd -T | grep -i maxstartups

رفع دائمی:
bash

# /etc/ssh/sshd_config روی هدف
MaxStartups 100:30:200
MaxSessions 50
LoginGraceTime 30

# whitelist کنترل‌نود در fail2ban
/etc/fail2ban/jail.local:
[sshd]
ignoreip = 10.0.0.0/24 <control-node-ip>

پیشگیری:

    forks = 20 حداکثر (نه ۵۰)

    serial: 10 یا serial: "30%" در playbookهای بزرگ

    مانیتورینگ sshd با متریک sshd_sessions

    ssh_args = ... -o ConnectTimeout=15 -o ServerAliveInterval=30 -o ServerAliveCountMax=3

1.2 SSH Error: data could not be sent to remote host

سناریو: اجرای متوالی چند playbook روی همان هاست، اتصال قطع می‌شود ولی ping کار می‌کند.

ریشه فنی: سوکت ControlPersist در ~/.ansible/cp/ خراب شده؛ یا pipelining=True با requiretty فعال در sudoers.

رفع فوری:
bash

rm -rf ~/.ansible/cp/*
# اگر مشکل تکرار شد موقتاً:
ANSIBLE_PIPELINING=False ansible-playbook site.yml

رفع دائمی:
bash

# /etc/sudoers روی هدف
Defaults:ansible !requiretty
Defaults env_keep += "SSH_AUTH_SOCK"

پیشگیری: مانیتورینگ حجم ~/.ansible/cp با cron پاک‌سازی روزانه؛ ControlPersist=300s نه 1h.
1.3 Too many authentication failures / Permission denied (publickey,password)

سناریو: کاربر deploy روی ۲۰۰ سرور، همه با SSH key، ولی روی یک هاست جدید خطا.

ریشه فنی:

    ssh-agent بیش از ۶ کلید لود دارد → MaxAuthTries 6 در sshd → fail

    authorized_keys روی هدف شامل کلید نیست

    SELinux context روی ~/.ssh/authorized_keys غلط (user_home_t به‌جای ssh_home_t)

    home directory permissions (755 باید باشد، نه 775)

    AllowUsers/AllowGroups در sshd_config

رفع:
bash

# دیباگ
ssh -vvv -i ~/.ssh/id_deploy -o IdentitiesOnly=yes deploy@host

# روی هدف
sudo sshd -T | grep -E 'AllowUsers|AllowGroups|MaxAuthTries'
ls -laZ ~deploy/.ssh/
sudo restorecon -Rv ~deploy/.ssh/

# تعداد کلیدهای agent
ssh-add -l
ssh-add -D  # پاک‌سازی و افزودن فقط کلید لازم

پیشگیری:

    ssh_args = ... -o IdentitiesOnly=yes

    در inventory: ansible_ssh_private_key_file=/etc/ansible/keys/deploy_ed25519

    automation برای چک authorized_keys با authorized_key module

1.4 Host key verification failed در محیط production

سناریو: پس از rebuild سرور، fingerprint عوض شده، playbook fail می‌شود.

ریشه فنی: host_key_checking=True (درست) ولی known_hosts قدیمی است.

رفع فوری:
bash

ssh-keygen -R hostname
ssh-keyscan -t ed25519,rsa hostname >> /etc/ssh/ssh_known_hosts
# یا اگر از CA استفاده می‌کنید:
# HostCertificatePath در sshd_config

رفع دائمی (production-grade):

    راه‌اندازی SSH Host CA با ssh-keygen -s ca_key -I hostname -h -n hostname -V +52w host_key.pub

    توزیع @cert-authority *.example.com ssh-ed25519 AAAA... در ssh_known_hosts

    غیرفعال‌کردن regenerating fingerprints در image

پیشگیری:

    Provisioning pipeline: بعد از هر rebuild، key از CM می‌آید نه regenerate

    known_hosts مرکزی در /etc/ssh/ssh_known_hosts با پیکربندی مدیریت‌شده

    host_key_checking=True هرگز در prod تغییر نکن

1.5 Connection reset by peer در مقیاس

سناریو: اجرای playbook روی ۱۰۰+ سرور، تعداد زیادی خطای گذرا.

ریشه فنی:

    forks بالا → burst اتصال

    sshd به MaxStartups می‌رسد

    load balancer / NAT session table پر می‌شود

    IDS/IPS rule trigger

رفع:
yaml

- hosts: all
  serial: 20
  max_fail_percentage: 10

پیشگیری:

    forks = 15-25 در محیط‌های بزرگ

    serial و throttle در taskهای شبکه‌ای:

yaml

- name: heavy network task
  uri: ...
  throttle: 5

    استفاده از ansible-runner یا AAP برای rate limiting

    اجرای rolling با serial: [1, 5, 20]

🔑 دسته ۲: احراز هویت و Privilege Escalation
2.1 Missing sudo password / sudo: a password is required

سناریو: کاربر جدید deploy بعد از rotating کلیدها، playbook fail می‌شود.

ریشه فنی: NOPASSWD حذف شده؛ یا become_ask_pass=False ولی رمز لازم.

رفع فوری:
bash

ansible-playbook -K site.yml
# یا
echo "password" | ansible-playbook -K site.yml  # ⚠️ ناامن

رفع دائمی:
bash

# /etc/sudoers.d/ansible (chmod 440)
ansible ALL=(ALL) NOPASSWD: ALL
Defaults:ansible !requiretty
Defaults:ansible !visiblepw
Defaults:ansible env_reset
Defaults:ansible secure_path="/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin"

پیشگیری:

    whitelist دستورات در sudoers (نه ALL):

text

ansible ALL=(root) NOPASSWD: /usr/bin/apt, /usr/bin/systemctl, /usr/bin/dpkg

    audit تغییرات /etc/sudoers.d/ با auditd

    تست sudo -n true در preflight playbook

2.2 Timeout (12s) waiting for privilege escalation prompt

سناریو: سرورهای جدید که در domain هستند، become هربار timeout.

ریشه فنی:

    sudo برای resolve نام کاربر، به LDAP/AD وصل می‌شود و کند است

    sudo prompt روی stderr با -v دیده نمی‌شود

    become_timeout پیش‌فرض 12 ثانیه کافی نیست

رفع:
yaml

# در playbook
- hosts: all
  become: true
  vars:
    ansible_become_timeout: 60

پیشگیری:

    /etc/nsswitch.conf: cache برای passwd/group (sss/systemd)

    sssd با cache_credentials = True

    NOPASSWD برای ansible در sudoers

2.3 Sorry, user ansible is not allowed to execute '/bin/bash' as root on host

سناریو: کاربر ansible با sudoers محدود، ماژول نیاز به shell دارد.

ریشه فنی: sudoers whitelist شامل /bin/bash نیست؛ یا become_method نیاز به دستور خاص دارد.

رفع: مجاز کردن دستور دقیق در sudoers، نه کل bash.

پیشگیری: استفاده از become_method: sudo با become_exe: /usr/bin/sudo و taskهای دقیق. اجتناب از shell: هرجا command: کافی است.
📋 دسته ۳: Inventory و متغیرها
3.1 undefined variable: ansible_facts['xxx']

سناریو: بعد از ارتقاء Ansible، playbook fail می‌شود که fact ناموجود است.

ریشه فنی:

    gather_subset محدود شده (مثلاً min بدون hardware)

    fact deprecated و حذف شده (مثلاً ansible_processor در نسخه جدید)

    gather_facts: false روی play

رفع فوری:
yaml

# چک کنید
- debug: var=ansible_facts
  when: ansible_facts is defined

# اضافه کردن subset لازم
- setup:
    gather_subset: ['all']

رفع دائمی:

    با ansible_facts['key'] (nested) استفاده کن نه ansible_key (flat)

    default() استفاده کن برای سازگاری:

yaml

"{{ ansible_facts.get('processor_count', 1) }}"

    inject_facts_as_vars = False و تعویض همه به nested

پیشگیری:

    ماتریس سازگاری نسخه‌ها در CI

    ansible-lint با rule no-undefined-vars

    تست --check روی staging قبل از prod

3.2 Could not match supplied host pattern, ignoring: <group>

سناریو: CI/CD pipe، گروه webservers در staging هست ولی در prod نیست، pipeline ساکت شکست می‌خورد.

ریشه فنی: گروه تعریف نشده؛ یا inventory داینامیک آن گروه را برنگرداند.

رفع فوری:
bash

ansible-inventory -i inventory/production --graph
ansible-inventory -i inventory/production --host web01

رفع دائمی:

    inventory_unparsed_failed = True

    assertion در ابتدای playbook:

yaml

- hosts: localhost
  tasks:
    - assert:
        that:
          - groups['webservers'] is defined
          - groups['webservers'] | length > 0

پیشگیری:

    schema validation برای inventory در CI

    ansible-inventory --graph در preflight

    استفاده از dynamic inventory با keyed_groups بجای hardcode

3.3 متغیرها به‌درستی override نمی‌شوند (variable precedence)

سناریو: مقدار http_port=8080 در host_vars ست شده ولی سرویس روی ۸۰ اجرا می‌شود.

ریشه فنی: اولویت متغیرها — role vars بالاتر از host_vars. یا set_fact در یه role دیگر.

رفع فوری:
yaml

- debug:
    var: http_port
- debug:
    msg: "{{ hostvars[inventory_hostname] | dict2items | selectattr('key','match','.*port.*') | list }}"

پیشگیری:

    ansible-inventory --host <name> برای دیدن متغیرهای مؤثر

    نام‌گذاری نقش‌محور: nginx_port, postgres_port (نه port)

    hash_behaviour = replace (پیش‌فرض، نه merge)

    مستندسازی matrix precedence در runbook

سناریو: ماژول selinux/apt fail با ImportError.

سناریو: یک فایل با vault-id dev رمز شده، ولی با --vault-id prod@... اجرا می‌شود.

ریشه فنی: vault-id mismatch بین encrypt و decrypt.

🔧 دسته ۶: ماژول‌های Package Management
6.1 apt lock: Could not get lock /var/lib/dpkg/lock-frontend

سناریو: اجرای playbook همزمان با unattended-upgrades یا cronی دیگر.

ریشه فنی: فقط یک apt lock می‌تواند فعال باشد.

رفع فوری:
bash

# روی هدف
sudo lsof /var/lib/dpkg/lock-frontend
sudo systemctl stop unattended-upgrades
sudo rm /var/lib/dpkg/lock-frontend  # فقط اگر پروسه مرده
sudo dpkg --configure -a

رفع دائمی:
yaml

- name: wait for apt lock
  shell: |
    while fuser /var/lib/dpkg/lock-frontend >/dev/null 2>&1; do
      sleep 2
    done
  changed_when: false

- name: wait for unattended-upgrades
  systemd:
    name: unattended-upgrades
    state: stopped
  ignore_errors: yes

پیشگیری:

    خاموش کردن unattended-upgrades روی سرورهای مدیریت‌شده توسط Ansible

    اجرای patch با پنجره مشخص

    serial: 10% برای apt

    apt با update_cache: yes و cache_valid_time: 3600
